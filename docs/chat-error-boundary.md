# 对话 HTTP 错误边界

状态：2026-10-14 已实现并完成离线验收，结果见 `chat-error-validation.md`。本轮为现有对话适配器的小范围修复，延续用户“接着干”的授权；不引入新的厂商或外部调用。

## 问题与范围

`OpenAiCompatibleChatProvider` 原先将 HTTP 错误正文、流内 `error` 对象，以及 JSON/网络异常的原始 message 写进异常、端点健康状态或日志。路由又会将异常描述写入降级记录，节点快照与运行回放因此可能重复保存上游回显的提示词或凭证。截取前几行并不能脱敏。

修复只修改该适配器与对应测试。目录继续使用既有 `integration` 和 `src/test/java/com/aiflow/engine/integration`；报告、独立 JAR 和哈希记录放既有 `target/ops/`，命名 `chat-errors-20261014-*`。保留所有旧产物。

## 错误契约

- HTTP 非 2xx 均为 provider 失败（包含不跟随的 3xx），只保留固定说明与数值状态码；直接关闭错误响应流，不读取或拼接错误正文。
- SSE 中出现非空 `error` 时抛固定错误，健康状态记录同一说明，不输出 `error` 内容或厂商自定义 code/type/message。
- JSON 非法片段仍按既有兼容策略忽略，DEBUG 日志只保留固定说明与 provider id，不包含片段或解析异常 message。
- 请求序列化、请求构造（含非法 header）、网络及流读取失败只提供固定分类说明；不把原始异常作为 cause/suppressed 链向上带出，避免打印堆栈时再泄露报文、凭证或 URL。
- HTTP、流内和网络/流读取失败仍只计一次健康失败；发送前的序列化/请求构造错误不改变健康状态。用户中断仍抛 `RunCanceledException`，不记录 provider 故障。
- 成功内容、usage、模型标识、图像请求格式、正常 SSE 拼接、路由顺序及“已经发出增量后不换档”的规则保持既有契约。这里只约束适配器生成的错误诊断，不对正常业务正文作脱敏。

## 验证

使用 JDK 本地 HTTP 桩与合成敏感标记，断言 HTTP/流内错误、非法片段日志、序列化及网络/流读取异常不会传播原文；同时验证健康失败计数、成功/取消及路由降级边界。先运行相关协议、路由、黄金集与错误响应测试，再运行全量离线测试和打包。不修改控制台，不触发浏览器验收；不变更数据库、配置、凭证、CI/CD 或依赖。

本轮不证明真实厂商兼容或模型质量；真实厂商激活仍等待用户提供协议、API 与模型额度。其他适配器和探活路径不包含在本次对话调用错误边界的交付声明中。
